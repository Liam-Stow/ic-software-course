Command automation

Module 6 ~22 min
🎯

By the end

One button press will aim the turret, spin up the shooter, wait until both are ready, and fire — all automatically.

The drivers want a single button that turns the turret to the target angle, speeds up the shooter, and fires the instant both are ready. We'll build that ShootSequence command by combining the AtTarget booleans from Lesson 23 with three new factories: Parallel, Sequence and WaitUntil.

Make a commands file

Things are getting complex enough to deserve their own file. Right-click src/main/cpp/ and make a new commands folder, and inside it a file named ShootingCommands.cpp. Do the same in src/main/include/commands/ for ShootingCommands.h.

Why a namespace?

We store these commands in a cmd namespace so their names can't clash with anything else in the project — just like canid protected our CAN IDs back in Module 2.

Set up the header with the namespace, the include, and the command declaration:

#pragma once #include <frc2/command/Commands.h> namespace cmd { frc2::CommandPtr ShootSequence(); }

Define ShootSequence in the body

In ShootingCommands.cpp, include the header and the three subsystems, then build the command. Because command files lean on the frc2::cmd factories so heavily, we add a using line to avoid typing the namespace every time:

#include "commands/ShootingCommands.h" #include "subsystems/SubShooter.h" #include "subsystems/SubTurret.h" #include "subsystems/SubFeeder.h" namespace cmd { using namespace frc2::cmd; frc2::CommandPtr ShootSequence() { return Parallel( SubShooter::GetInstance().SpinFlywheel(), SubTurret::GetInstance().TurnTo(30_deg), Sequence( WaitUntil([] { return SubShooter::GetInstance().AtTarget(); }), WaitUntil([] { return SubTurret::GetInstance().AtTarget(); }), SubFeeder::GetInstance().Feed() ) ); } }
Keep using namespace out of headers

The using namespace frc2::cmd; line is fine in a .cpp command file, but never put it in a .h header — headers get included all over the project, and the shortcut would leak everywhere and cause name clashes.

Reading the composition

Parallel(...) runs everything inside it at the same time: the flywheel spins up and the turret turns and the inner Sequence runs — all together. The Sequence runs its steps one after another: first WaitUntil the shooter is at target, then WaitUntil the turret is at target, and only then Feed() the ball. The two [] {...} lambdas are little yes/no questions that WaitUntil keeps asking until the answer is true.

Bind it to a button

In RobotContainer.cpp, include the commands file and put ShootSequence on the A button. We'll also keep two buttons to swing the turret manually for testing:

void RobotContainer::ConfigureBindings() { _controller.A().WhileTrue(cmd::ShootSequence()); _controller.X().OnTrue(SubTurret::GetInstance().TurnTo(30_deg)); _controller.Y().OnTrue(SubTurret::GetInstance().TurnTo(0_deg)); }
Watch the sequence play out

Simulate and plot all the subsystems together. Press A and you'll see:

  • Shooter and turret both start moving immediately (Parallel).
  • Each reaches its target at its own pace.
  • Only once both AtTarget booleans are true does the feeder run.
  • Release A and the shooter and feeder stop. 🎉
? What does WaitUntil do in the sequence?
WaitUntil holds the sequence until the lambda returns true — that's how we wait for the shooter and turret to actually reach target before feeding.
? Why is the feeding logic inside a Sequence but the whole thing inside a Parallel?
Parallel starts the flywheel, the turret, and the wait-then-feed chain all at once; the inner Sequence makes sure feeding only happens after both are on target.
